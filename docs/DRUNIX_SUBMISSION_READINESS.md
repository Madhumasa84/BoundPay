## Submission narrative

| Item | Review-ready text |
| --- | --- |
| Title | **BoundPay: Shared Spending Authority for AI Agents** |
| Problem | An owner may allow an AI agent to buy within a limit, but two separately operated checkout services can each see enough local headroom and collectively exceed one intended allowance. An external payment may also be accepted while its response is lost, so a timeout cannot safely free the allowance. |
| Solution | The owner issues a signed BoundPay Authority Passport and a smaller shared Drunix mandate. Named participants reserve unique purchase intents against one ledger balance. Each service waits for a `VALID` reservation commit, matching readback, and a `VALID` one-time dispatch claim before calling its configured payment adapter. A named verifier records success or definitive failure; uncertain outcomes retain their hold. Revocation prevents new reservations after commit. |
| Target users | Agent-commerce platform operators, enterprises delegating limited purchasing authority, separately operated payment/checkout services, and reviewers who need a common authorization trail. |
| Architecture | Two Next.js/SQLite BoundPay services with distinct MSP client identities → Go chaincode on the permissioned Drunix channel → each service's explicitly configured MOCK or Razorpay TEST payment adapter → a named outcome verifier. Product/cart details, provider credentials, and salts stay off public ledger state. |
| Drunix contribution | Shared mandate state, certificate-scoped participant permissions, multi-org endorsement, MVCC conflict validation, commit status and queryable transaction IDs. The local sample has Org1 and Org2 on **one developer-controlled Docker host**. |
| Differentiation | Signed Passport terms, atomic allowance across two service identities, confirmed ledger commits before dispatch, and a durable unknown-outcome recovery path are combined and exercised end to end on Drunix. Shared budgets, spending mandates and unknown-outcome holds have substantial prior art; this is a tested integration, not a new or first primitive. See the [prior-work comparison](./DRUNIX_PHASE2_IMPLEMENTATION.md#distinctive-contribution-and-prior-work). |
| Prior prototype disclosure | BoundPay already had deterministic policy, local SQLite reservations, exact human approval, signed Authority Passports/decision receipts, MOCK payments, and a Razorpay TEST adapter with historical TEST evidence. This challenge upgrade added the Go Drunix contract, Gateway integration, shared mandate/outbox/recovery state, two-service demonstrations, and the shared-authority UI. The old Razorpay evaluation is preserved in its isolated checkout. |

### Why a ledger here

For one trusted operator, an atomic centralized database is simpler and faster. Drunix is useful when genuinely separate participants must enforce and inspect one allowance without letting any one participant's database be the sole authority. They still trust the channel administrators, MSP/CA enrollment, orderer and committing peers, chaincode lifecycle/endorsement policy, Passport issuer, and outcome verifier. The recorded sample does **not** prove those parties are independently governed. A Drunix outcome is a verifier attestation, not independent evidence that a bank settled a payment.

## Acceptance review and remaining risks

| Phase 1 criterion | Current evidence / limit |
| --- | --- |
| Pinned setup and compilation | Drunix source `v1.0.0` at `3fb2b135a5b2adf7e1071d9b1624052a1bbb1772`, Go `1.23.0` container, image digests and locked Node dependencies are recorded in Phase 2. A fresh Git clone of local commit `7a3b54d` passed `pnpm install --offline --frozen-lockfile` with 511 cached packages, key generation, migration, seed, authority validation, production build and the pinned Go contract test. Type checking and linting passed on the same committed source. A fresh `boundpay-review` channel accepted version `1.2`, lifecycle sequence `1`, with Org1/Org2 approvals; the already-running Docker sample network was used, so this is not cold-network boot evidence. |
| External client and commit evidence | Standard Fabric Gateway Node `1.10.0` worked experimentally against the actual Drunix network. The client checks `VALID` and queries committed state before dispatch; the official Drunix repository does not guarantee this external SDK. |
| Separate services and concurrency | The contract demo spawns two Node worker processes with Org1MSP/Org2MSP certificates. The HTTP demo starts separate production-mode Next processes on ports 3211/3212 with independent SQLite files and different application signing keys. No shared in-memory or BoundPay SQLite lock coordinates the two services. A 500,000-paise mandate admitted one of two concurrent 300,000-paise holds; the exact 200,000-paise remainder could be reserved and a further request was rejected. |
| Dispatch, retries and replay | The losing reservation had no provider dispatch. Same-content retries are idempotent; changed-content ID reuse, unauthorized issue/spend/revoke/outcome operations, and terminal redispatch are rejected. A durable `MAY_HAVE_SENT` marker prevents blind resend after restart. |
| Recovery | Tests covered pre-dispatch ledger outage and restart, provider timeout with retained `UNKNOWN` hold, a mock order-created/response-lost scenario, and replay of an already committed outcome after local acknowledgement loss. Inconclusive provider lookup remains held. A real Razorpay TEST crash-after-acceptance or settlement was not exercised. |
| Revocation and review | Committed revocation blocks subsequent reservations. Earlier reservations may still be resolved, and dispatched payments are not cancelled. The named Org1 verifier identity read back the mandate and reservation transaction IDs from Drunix. |
| Privacy | Public state holds allowance, amount, identities, states and salted commitments; raw purchase proof and Passport are transient, and scope terms use the private collection. Fresh 32-byte salts defeat dictionary guesses of predictable product/amount values while secret. Endorsing peers can see transient data; copied keys, compromised member hosts and raw outbox backups are trust risks. |
| Existing protections | Local deterministic policy, exact human approval, signed Passport checks and explicit payment modes remain. Chaincode enforces mandate bounds and identity, but cannot itself prove local human presence, mutable daily policy or trusted Passport wall-clock expiry. Directly credentialed participants must be trusted to use compliant BoundPay services. |

**Duplicate-payment boundary.** One ledger dispatch claim does not make an external provider operation exactly once. The service writes `MAY_HAVE_SENT` before the provider call, refuses automatic resend after that point, and keeps uncertain amounts reserved. A crash immediately after this marker can leave a payment that was never sent; a crash after provider acceptance can leave a payment that was sent. Both require same-attempt provider lookup or manual reconciliation. Razorpay's documented unique receipt protects order creation only; it does not prove one capture or bank settlement. The demo uses an in-process MOCK adapter, and its state disappears on restart.

**Verifier boundary.** The local HTTP demonstration supplies the sample verifier certificate to both test processes so either can record its locally checked synthetic outcome. The contract still rejects identities outside its verifier allowlist, but this topology does not demonstrate an independent reviewer or safe production key custody. The separate reviewer readback in the contract demo uses the named Org1 Admin identity. A real deployment needs separately governed verifier credentials and provider evidence checks.

## Measured local result

Client wall-clock timings from three successful contract-demo runs on 2026-09-27, including one run on the fresh `boundpay-review` channel. Environment: Linux WSL2 x86_64, Node `v20.20.2`, pnpm `10.33.0`, Docker Engine `29.6.1`, Compose `5.3.0`, Drunix `v1.0.0` sample network with both organizations on one host, Go chaincode `v1.2`. Each run contributed the winning concurrent reserve and two later new successful reserves; duplicate retries were excluded. `submitAsync` invocation to `VALID` commit status was **2,330–3,801 ms, median 2,557 ms (n=9)**. Time from `submitAsync` returning to the `VALID` commit status was **2,201–3,239 ms, median 2,414 ms (n=9)**. The three issue operations took 2,746–5,332 ms (median 3,107 ms), and three dispatch claims took 2,299–2,526 ms (median 2,478 ms), measured from client call to `VALID` status. Queries, UI and payment-adapter time are excluded. This tiny, uncontrolled local sample is not a throughput, national-scale, real-time payment, or production latency claim.

Observed functional result on the two-service HTTP run: two 279,900-paise requests raced against 500,000 paise; one MOCK payment was confirmed and one request was blocked. After a separate 89,900-paise ambiguous attempt and one 89,900-paise recovered no-send purchase, the ledger showed 369,800 settled, 89,900 reserved/unknown, and 40,300 available. The amount labeled settled is a **synthetic verifier attestation**.

## Three-minute demo script

Preflight before the three-minute presentation: complete the [pinned network and app setup](./DRUNIX_PHASE2_IMPLEMENTATION.md#drunix-source-versions-and-deployment), build the app, confirm the two demo ports are free, and use `PAYMENT_ADAPTER_MODE=MOCK`. Keep the terminal output and `/shared-authority` page visible; allow `DRUNIX_DEMO_REVIEW_SECONDS=90` to hold both HTTP processes open for inspection. Ledger operations can vary in duration, so retain an unedited recording of a successful run as a fallback; do not describe replayed output as a new live run.

| 1:15–1:55 | Show the 89,900-paise `UNKNOWN` hold after a synthetic timeout, the service restart, and the refused retry. Explain that missing provider evidence never releases or resends it. Reconciliation retains the hold. |
| 1:55–2:30 | Show the contract demo's prospective revocation: a new Reserve fails; an earlier hold can be resolved. Use the named reviewer identity to query the same mandate and reservation evidence with `node scripts/drunix-shared-authority-demo.mjs --inspect-mandate <printed-mandate-id>` (set `DRUNIX_CHANNEL` to the demo channel). |
| 2:30–3:00 | State the trust boundary: “These are real local Drunix commits and MOCK payments. The verifier attests to an outcome; the ledger does not prove settlement. Both organizations currently run on my test host.” |

For a response-loss variant, run `DRUNIX_DEMO_AMBIGUOUS_FAULT=SIMULATE_RESPONSE_LOSS pnpm run shared-authority:drunix-app-demo`; the mock creates an order before returning an unknown response. Its in-memory provider state is lost on service restart, so the reservation stays held for manual reconciliation. Do not describe that as a completed real provider recovery.

## Reproduce and review

1. Use the isolated upgrade branch. Run `cp .env.example .env`, `pnpm install --frozen-lockfile`, `pnpm run authority:keys`, `pnpm run db:migrate`, `pnpm run db:seed`, `pnpm run authority:validate`, `pnpm run build`, `pnpm run typecheck`, `pnpm run lint`, and `pnpm test`. Keep generated keys, `.env`, databases and provider credentials outside source control. The demo script creates and removes its own short-lived application signing keys.
2. Clone the official [Drunix v1.0.0 repository](https://github.com/npci/drunix/tree/v1.0.0), verify the commit above, run `./scripts/prepare-drunix-local-network.sh /tmp/drunix-v1.0.0`, then follow [the exact network/channel/chaincode commands](./DRUNIX_PHASE2_IMPLEMENTATION.md#reproduce-the-local-network-and-chaincode). Use the tested Org1/Org2 `AND` endorsement policy and private collection. From the chaincode directory, run the pinned `scripts/drunix-toolchain/go test -mod=readonly ./...` wrapper.
3. From the BoundPay root, run `pnpm run shared-authority:drunix-demo` and `DRUNIX_DEMO_REVIEW_SECONDS=90 pnpm run shared-authority:drunix-app-demo`. For a distinct fresh channel, set `DRUNIX_CHANNEL=boundpay-review` in both commands after deploying version `1.2`, sequence `1`, there. The direct demo prints a mandate ID for reviewer readback. The app demo prints a separate-mandate ID, service ports, transaction IDs, and MOCK labels.
4. Run `pnpm run test:e2e` after `pnpm run build`. It resets only its documented `/tmp/boundpay-e2e.sqlite` fixture. Stop the sample network with the runbook's `./network.sh down` command when its ledger evidence is no longer needed; remove only the exact printed temporary demo directory after review.

## Track and eligibility

The strongest **publicly evidenced** track fit is **Real-Time Payments**, specifically shared pre-dispatch authorization and handling ambiguous payment outcomes. The demo does not accelerate or implement a real-time rail; its external payment is MOCK. The user-supplied **CHL-7007 / Innovative Fintech Ideas** label may be a better conceptual fit if that category appears in the registered portal, but no accessible official problem statement verifies it. Confirm those directly in the organizer portal before any submission. There is no asset-tokenization, cross-border-remittance, or financial-inclusion feature in this build.
